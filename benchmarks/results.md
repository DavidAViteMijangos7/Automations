## Why triage loses

`triage` is slower. Hiding that would waste the benchmark, so here is where the
time actually goes.

The headline gap is **not** in hashing or reading — it is entirely in the
directory walk. Compare the phase table above: `triage` finishes the
hash-and-read phase *faster* than `xlsreport` (5.395 s vs 6.561 s), then loses
almost 8 seconds walking the tree (8.498 s vs 0.858 s).

`benchmarks/diagnose_cpp.cpp` isolates the primitives. Warm-cache figures from
three consecutive passes on the same 50,000-file tree:

| Primitive | Result |
| --- | --- |
| Scalar SHA-256 (`triage::Sha256`) | 405–423 MiB/s |
| `fopen`/`fread`, all 50,000 files, warm | 114–149 MiB/s (0.068–0.089 ms/file) |
| `std::filesystem::recursive_directory_iterator` + `file_size` | 4.28 / 5.31 / 4.80 s |
| Win32 `FindFirstFileW` (same work) | 0.35 / 0.48 / 0.45 s |

Two conclusions:

1. **The hand-written SHA-256 is not the bottleneck.** At ~415 MiB/s it spends
   roughly 0.4 s on the 173 MiB it actually hashes. The rest of the hash phase
   is per-file open/read overhead across 42,502 files.
2. **`std::filesystem` costs ~10x versus the raw OS call.** On this toolchain
   (MinGW-w64 GCC 16.1.0, libstdc++) `is_regular_file()` and `file_size()` each
   issue their own stat call per entry instead of reusing what the directory
   scan already returned. Python's `os.scandir` returns the size inside the same
   `FindFirstFileW` record, which is why it lands at 0.858 s — right next to the
   0.45 s Win32 floor, and ~10x under `std::filesystem`.

So the result is a standard-library quality gap on this platform, not a language
gap. A Win32 (or `getdents`) fast path in the walk would very likely flip the
overall result; it was left out deliberately to keep the two implementations
algorithmically identical, which is the comparison this benchmark was set up to
make.

## Known measurement caveats

- **Working-set memory is unmeasurable on this host.** `GetProcessMemoryInfo`
  and PowerShell `Get-Process` both report ~5 MiB for *every* process, including
  a control that allocated and dirtied 300 MiB. The reported `Peak commit`
  column uses the job-object `PeakProcessMemoryUsed` counter instead, validated
  against 200 MiB and 400 MiB controls (208.6 MiB and 409.0 MiB).
- **Cold-cache reads are ~40x slower and dominate everything.** The first
  diagnostic pass measured 2.7 MiB/s reading all 507 MiB cold, versus
  114–149 MiB/s warm. `run.py` therefore warms the cache before timing; the
  numbers above describe warm-cache behaviour only.
- **`triage.exe` needs the MinGW runtime DLLs on `PATH`** (`libstdc++-6`,
  `libgcc_s_seh-1`, `libwinpthread-1`). Without them it exits 127 with no
  output. Not an issue in CI, where Linux `g++` links against the system
  `libstdc++`.
